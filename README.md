# Куку! / Kuku!

Мессенджер на Kotlin Multiplatform с общим интерфейсом Compose Multiplatform для Android и iOS.
Этот репозиторий содержит клиент; для обмена сообщениями нужен совместимый сервер.

## Возможности

- Вход по email-коду, управление профилем и сессиями.
- Личные и групповые чаты, ответы на сообщения и вложения.
- Локальная история, черновики и очередь отправки для работы без сети.
- Обновления через WebSocket и восстановление соединения.
- Поиск пользователей, управление группами и администрирование с учётом прав доступа.

На Android авторизованное соединение обслуживает foreground-служба. История чатов читается
из Room и пополняется с сервера страницами; сервер не нужен для просмотра уже сохранённой истории.

## Быстрый старт

### Android

Требуются JDK 21 и Android SDK Platform 37. Минимальная версия устройства — Android 8.0 (API 26).

1. Откройте корень репозитория в Android Studio с поддержкой используемых Kotlin и Android Gradle Plugin.
2. Укажите JDK 21 для Gradle. Путь к Android SDK задайте через `ANDROID_HOME` или `sdk.dir` в локальном `local.properties`.
3. Дождитесь синхронизации Gradle и запустите конфигурацию модуля `androidApp`.

Сборка APK из PowerShell:

```powershell
.\gradlew.bat :androidApp:assembleDebug
```

На macOS/Linux ту же задачу можно вызвать через `sh ./gradlew :androidApp:assembleDebug`.
APK появится в `androidApp/build/outputs/apk/debug/`.

### iOS

Требуются macOS, Xcode с iOS SDK, JDK 21 и Android SDK для конфигурации общей Gradle-сборки.
Минимальная версия приложения в Xcode-проекте — iOS 17. Подключены цели iOS ARM64 и симулятор ARM64.

Откройте `iosApp/iosApp.xcodeproj`, выберите схему `iosApp` и симулятор.
Для запуска на устройстве настройте Signing & Capabilities своей команды Apple Developer.

### Подключение к серверу

При первом запуске укажите хост и порт своего сервера с корректным TLS-сертификатом.
После проверки соединения введите разрешённый на сервере email и полученный код.
Настройка сервера, допуска пользователей и отправки писем выполняется отдельно от клиента.

## Структура проекта

| Модуль / каталог | Назначение |
|---|---|
| `androidApp`, `iosApp` | Платформенные приложения |
| `shared-ui` | Общая оболочка, навигация и сборка DI |
| `feature-*` | Экраны и ViewModel отдельных функций |
| `shared-domain` | Модели приложения и интерфейсы репозиториев |
| `shared-data` | Сеть, Room и реализации репозиториев |
| `core-runtime` | Жизненный цикл соединения и фоновой службы |
| `core-ui` | Общие компоненты интерфейса и ресурсы |
| `build-logic` | Общие Gradle-плагины и правила зависимостей модулей |
| `contracts` | Локальный серверный контракт для тестов (не хранится в Git) |
| `ci` | Скрипты проверок Android и iOS |

Архитектура — feature-модули, MVVM и разделение presentation/domain/data.
Features работают с интерфейсами domain; реализации подключаются в общем DI-контейнере.

## Проверки и сборка релиза

Android: debug/release, AAB, host-тесты, общие Kotlin metadata и lint:

```powershell
.\ci\check-android.ps1
```

iOS: native-тесты и сборки Xcode без подписи, выполняются на macOS:

```sh
sh ci/check-ios.sh
```

Контракт не хранится в Git. Перед полным локальным прогоном тестов разместите
его файлы в `contracts/v0.1.0` или передайте внешний каталог через Gradle-параметр
`-PcontractDirectory=<каталог>`. Для Android-скрипта используйте `-ContractDirectory <каталог>`.
Обычная сборка приложения контрактных файлов не требует.

Публичный GitHub CI запускает Android-проверки с `-SkipContractTests`: выполняются
сборки, lint и тесты клиента, кроме `PublishedContractTest`, которому нужен приватный
контракт. Это не проверка совместимости с серверным контрактом. Для такого же локального
прогона используйте `.\ci\check-android.ps1 -SkipContractTests`. Без этого флага
контрактные тесты обязательны; отсутствие файлов считается ошибкой.

Android release использует R8 и уменьшение ресурсов. Для подписи задайте переменные окружения
`RELEASE_STORE_FILE`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS`, `RELEASE_KEY_PASSWORD`.
Без них release собирается неподписанным. Ключи и пароли в Git не добавляются.

## Автоматический Android release на GitHub

Workflow `Publish Android release` запускается при push тега `vMAJOR.MINOR.PATCH`
(например, `v0.1.0`). Он проверяет Android-тесты клиента и release lint, собирает
подписанные APK/AAB, проверяет подпись APK и создаёт GitHub Release с файлами и SHA-256.
Приватные контрактные тесты и iOS в этот workflow не входят.

### Один раз: создать ключ

В Android Studio откройте **Build → Generate Signed Bundle / APK → APK → Next → Create new**.
Сохраните keystore вне репозитория, задайте пароль хранилища, alias (например, `kuku`),
пароль ключа и срок действия не менее 25 лет. Для совместимости можно использовать
одинаковый пароль ключа и хранилища. Заполните сведения сертификата: они публичны в APK,
поэтому используйте подходящее имя издателя, а не личные данные, которые не хотите публиковать.
Сохраните резервную копию ключа и паролей: дальнейшие APK-обновления подписываются тем же ключом.
Не используйте debug.keystore для выпуска. После создания ключа мастер можно закрыть;
сборку выполнит GitHub.

### Один раз: добавить GitHub Secrets

Откройте репозиторий → **Settings → Secrets and variables → Actions → New repository secret**.
Добавьте четыре секрета:

| Имя | Значение |
|---|---|
| `RELEASE_KEYSTORE_BASE64` | Файл keystore, закодированный в Base64 |
| `RELEASE_STORE_PASSWORD` | Пароль хранилища |
| `RELEASE_KEY_ALIAS` | Alias созданного ключа |
| `RELEASE_KEY_PASSWORD` | Пароль ключа |

Чтобы скопировать Base64 в буфер обмена PowerShell, подставьте путь к своему keystore:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\path\to\kuku-release.jks')) | Set-Clipboard
```

Вставьте результат только в поле секрета `RELEASE_KEYSTORE_BASE64`. Base64 не шифрует ключ:
не сохраняйте эту строку в исходниках или переписке. После добавления очистите буфер обмена.
Ключ на runner восстанавливается во временный файл и удаляется после сборки. При отсутствии
секретов выпуск останавливается; debug-подпись и неподписанный APK не используются.

### Выпустить версию

Сначала закоммитьте и отправьте код и workflows. Затем создайте тег на нужном коммите
и отправьте его на GitHub (в терминале Android Studio):

```sh
git tag v0.1.0
git push origin v0.1.0
```

Версия приложения берётся из тега. `versionCode` равен `1000 + github.run_number`
этого workflow; повторный запуск того же workflow run сохраняет код версии.
Для следующих выпусков создавайте новые теги (`v0.1.1`, `v0.2.0`), не переносите старые.
Если приложение уже выпускалось другим способом, обеспечьте рост `versionCode` относительно
опубликованных сборок перед переходом на эту схему.

После успешного запуска скачайте APK из **Releases → нужная версия → Assets**.
AAB предназначен для загрузки в магазин и напрямую на телефон не устанавливается.
Копия файлов и R8 `mapping.txt` хранятся в **Actions → запуск → Artifacts** 30 дней;
сохраните mapping для каждой выпущенной версии. Публикация не зависит от доступности iOS CI.

Для ручного запуска откройте **Actions → Publish Android release → Run workflow** и укажите
существующий тег. Уже опубликованный Release автоматически не перезаписывается.
При частичной ошибке публикации проверьте Assets существующего выпуска, прежде чем повторять её.

APK, установленный ранее с debug-подписью Android Studio, нельзя обновить APK с новым
release-ключом. Это разные подписи; не удаляйте установленное приложение без учёта его локальных данных.
